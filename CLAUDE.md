# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

watchtower-server tracks the price/discount/availability of observables across the web. A Lapis (Lua/OpenResty) HTTP API server manages observables, scraper site definitions, notification channels, users/roles/API keys, and a boolean-expression rule engine, and serves the frontend. Workers (an embedded worker inside the server, and/or standalone worker processes) observe observables on a schedule, ingest observations, and let the rule engine turn matching observations into alerts.

Git-initialized (`main` branch). `.github/workflows/test.yml` runs the frontend vitest suite and confirms the server/worker Docker images build, on every push/PR; `.github/workflows/docker-publish.yml` builds/publishes the image on version tags. There is no Lua test suite, only a frontend vitest suite (see below).

## Commits

Every commit in this repository must carry sign-off trailers from **both** the developer and Claude — this supersedes the harness's default `Co-Authored-By`/`Claude-Session` commit footer. Use `git commit --signoff` (`-s`) to add the developer's own trailer (from their configured `user.name`/`user.email`), plus an explicit trailer for Claude:

```
Signed-off-by: <developer name> <developer email>
Signed-off-by: Claude <noreply@anthropic.com>
```

## Development commands

All development happens through the dev Docker Compose stack; there is no local Lua toolchain expected on the host.

```console
cd dev
docker compose up -d              # server, db, frontend (worker is idle by default, see below)
docker compose stop
docker compose down -v            # also drops the db volume - needed after any schema change
```

- `server/` and `shared/` are bind-mounted into the `lapis` container for live editing — restart the container to pick up changes (`lua_code_cache` is off in dev, but `init_worker_by_lua_block` code — `bootstrap_admin.lua`, the embedded worker — only runs once at boot, so those specifically need a restart). **This applies broadly whenever the embedded worker is enabled** (`USE_EMBED_WORKER=1`, the dev default, along with its independent `USE_EMBED_SCHEDULER=1`/`USE_EMBED_DELIVER=1`/`USE_EMBED_EVALUATOR=1` flags): `server/workers/observe_pending_worker.lua` and everything it constructs at boot (`observer_registry`, `scheduler_service`, `embedded_sender`, `delivery_queue_service`, job/model instances) are held in module-level closures for the life of the nginx worker process, so editing anything reachable from that boot-time setup — e.g. `shared/watchtower_worker_core/notification_senders.lua`, `shared/watchtower_worker_core/pollers/notify.lua`, `shared/watchtower_worker_core/pollers/evaluate.lua`, `shared/watchtower_worker_core/processors.lua`, `server/plugins/scheduler/services/scheduler.lua`, `server/plugins/jobs/services/jobs.lua`, `server/plugins/notification_channels/services/delivery_queue.lua` — has **no effect** until `docker compose restart lapis`. If a change to code like this doesn't seem to take effect, restart before assuming it's a code bug.
- The `worker` dev container mounts `worker/lua` and `shared/`, but its entrypoint is overridden to `tail -f /dev/null`; exec in and run `lua main.lua` manually while iterating (needs a real `SERVER_API_KEY` and a `WORKER_CONFIG_FILE` — see `docker/worker/worker_config.example.lua`).
- The `db` service auto-loads `config/dataset/init.sql` on first boot (Postgres `docker-entrypoint-initdb.d`). There is no migration system — changing the schema means editing that file and recreating the volume (`docker compose down -v`).
- The `frontend` service runs `yarn && yarn dev` on Node 22 (Tailwind 4's `@tailwindcss/oxide` needs >= 20; vitest 4's toolchain transitively needs >= 22).

Frontend tests (vitest; there is no Lua test suite):

```console
cd public && yarn install && yarn test
```

The API contract is documented in `docs/openapi.yaml`; the full `WORKER_CONFIG_FILE` reference is `docs/dev/worker-configuration.md` (see `docker/worker/worker_config.example.lua` for a runnable example of the same file).

## UI verification

The frontend (`public/`) has no automated UI/e2e test suite beyond vitest unit tests. Verify UI changes by actually driving them in a browser, not by trusting Vite's hot-reload logs alone:

- If the `claude-in-chrome` extension is installed and available, use it to drive the browser directly.
- Otherwise, write a Python script using Playwright (`playwright.sync_api`) that logs in, exercises the flow under test, and asserts on the resulting DOM state and/or network requests. Put these scripts in a scratch/temp directory — they're throwaway verification tooling, not part of the repo.

## Architecture

### Server (`server/`) — Lapis app on OpenResty

Entry point: `server/app.lua`, run via `lapis server development|production` (see `docker/images/{dev,prod}/*/Dockerfile`). Plugins register themselves through `lib/plugins-service.lua` (topologically sorted by `dependencies`, each plugin's `setup(app, deps)` return value handed to any plugin that declares it as a dependency — mirrored exactly, name for name, by the frontend's `public/src/core/services/plugin-service.js`). Registration order in `app.lua`: `security`, `rules`, `alerting`, `entities`, `workers`, `scheduler`, `jobs`, `notification_channels`, `observer_configs`.

- **`plugins/security/`** — users, roles, API keys, JWT + API-key auth, RBAC. `services/{auth,auth_jwt,auth_api_key,rbac,users,roles,store_api_key,rate_limit,password_hash,secure_compare}.lua`. `setup()` returns `{auth, rbac, rate_limit, users, roles, perms}`; every other plugin declares `dependencies = {'security'}` and wraps its routes in `compose(auth:with({require=true}), rbac:with(perms.X), ...)`. Enforcement is always a live DB read, never a token claim: `auth.lua` 401s on `user.enabled == false` on every request; `rbac.lua` resolves permissions via `roles:get_permissions(role_id)` (an `invalidate()`-on-mutation cache), never the JWT's own `role` claim; `auth_api_key.lua` re-intersects a key's stored permissions with its owner's _current_ permissions on every use. `permissions.lua` is the fixed permission catalog (mirrored by hand in `public/src/constants/permissions.js` — keep both in sync). The first admin account is bootstrapped idempotently at server boot from `INITIAL_ADMIN_USERNAME`/`INITIAL_ADMIN_PASSWORD` by `server/workers/bootstrap_admin.lua`, required from `nginx.conf`'s `init_worker_by_lua_block` (not from `app.lua`'s top level — that module is `require`d fresh on every request in dev with `lua_code_cache off`, and real DB I/O inside a module body hits OpenResty's "attempt to yield across C-call boundary"; the actual insert runs inside an `ngx.timer.at(0, ...)` callback instead).
- **`plugins/rules/`** — the condition DSL. `shared/rule_engine/source.lua` parses a flat, YAML-_like_ (deliberately not real YAML — see its header) rule document (`name`/`if`/`enabled`, optional `description`/`severity`/`tags`/`cooldown_seconds`); `if` is a boolean expression evaluated by `shared/rule_engine/expr.lua` (hand-rolled recursive-descent parser + evaluator) over the fields declared in `allowed_fields.lua` — `source`, `observable_id`, `worker`, `observable_type`, `payload`, and `payload.*`. This vocabulary is deliberately agnostic to each observable type's own _schema_: no observation-schema field (e.g. "product"'s price/discount/available/url) is ever a directly-nameable field, since an observable type's own field names/shapes vary — they're only reachable via `payload.<name>`; `worker` (the reporting worker's id) and `observable_type` (the observable type's own `name`, letting a rule target one type directly, e.g. `observable_type = "product"`) are both universal observation metadata, so they're exposed directly. `services/rule_engine.lua` finds every enabled rule (cached, `invalidate()`d on any rule mutation) matching a given context and returns one `{id, severity, tags, cooldown_seconds}` per match — `cooldown_seconds` (optional, `>= 0`) is an anti-spam window: the analyzer (`shared/watchtower_worker_core/rule_matching.lua`, the orchestration both `shared/analyzer.lua` and `worker_rule_matcher.lua` share) skips creating another alert for that rule+observable pair if one already fired within that many seconds of the last one (a live join query against `alerts`/`observations`, not a cache, so it stays correct across nginx worker processes). `POST /api/rules/test`/`test-expression` expose this read-only; the frontend's rule creation form (`public/src/plugins/rules/views/RuleFormView.vue`) shows a live "Available fields" reference panel listing this generic vocabulary plus, per observable type (fetched from `GET /api/observable_types`), the `payload.<name>` fields that type's `observation_schema` actually declares. Import/export: `GET /api/rules/export` (optionally `?ids=`) downloads a single `.yaml` for exactly one matching rule, or a `.zip` (one `.yaml` per rule) for 2+, built by a hand-rolled writer (`lib/zip_writer.lua`/`lib/crc32.lua`) rather than adding a new Luarocks zip dependency; `POST /api/rules/import/preflight` (multipart `file`, sniffed for the zip magic bytes rather than trusted by extension — `lib/zip_reader.lua` FFI-binds straight to the system's `libz.so.1` for DEFLATE, no new dependency there either) parses+validates every candidate through the same `_derive` create/update already use, flagging a `name` collision with an existing rule as a `conflict` for the frontend's `RuleImportDialog.vue` to resolve (skip/update/create-new) without writing anything; `POST /api/rules/import` then commits that client-resolved `{source, action, existing_id?}[]` array, one `pcall`'d create/update per item (skip-and-report, never abort-the-batch) — gated on both `RULES_CREATE` and `RULES_UPDATE` since one batch can do either.
- **`plugins/alerting/`** — mostly read + delete over _fired_ alert instances. Alerts are created by `"analyzer"`-role workers, never as a side effect of `POST /api/observations` (see `plugins/entities/` below): the embedded worker creates them in-process (`shared/analyzer.lua`), and `POST /api/alerts` (permission `alerts:create`, distinct from `alerts:read`/`update`/`delete` — held by the seeded `admin`/`operator` roles, not `viewer`) exists for a caller that already made its own rule-match-and-cooldown decision and just needs the resulting row inserted — today that's `shared/watchtower_worker_core/worker_rule_matcher.lua`, the standalone worker's own client-side rule-matching path for the `analyzer` role (see "Shared pipeline" below); the route itself does no matching/cooldown logic, only input validation (`observation_id` must reference an existing observation, `severity` one of the four allowed values). Each alert carries a `severity` (`low|medium|high|critical`, from the matching rule's `severity`) with a derived `severity_value` for sorting. `alerts` deliberately carries no notification/delivery information of its own — that lives in the sibling `alert_deliveries` table (`server/models/alert_deliveries.lua`), keyed per `(alert_id, channel_id)` since one alert can route to several channels via several matched `notification_policies` (see `plugins/notification_channels/` below); `GET /api/alerts` enriches its response with a `deliveries` array via a `json_agg` subselect, the same enrichment pattern it already uses for `source`/`payload`/`rule_name`, rather than owning those columns itself.
- **`plugins/entities/`** — observable-type-driven Observables/observations, replacing the old product-only `plugins/items/`+`plugins/observations/` pair (`observations` was itself renamed from `monitoring`/`/api/monitors` to free `monitors` — now `workers` — for the registry below). `observable_types_routes.lua` owns `observable_types` (each with a `properties` schema for creating Observables, and an `observation_schema` for what an observation records — see `lib/property_schema.lua`); `observables_routes.lua`/`observations_routes.lua` validate against those schemas. `POST /api/observations` requires `worker_id` (which worker produced this observation) but does nothing beyond validating `properties` against the schema and inserting the row — it deliberately does not run rule matching inline (an earlier design synchronously called `shared/analyzer.lua` in-request here, which violated this file's own "worker jobs never run in an API endpoint" rule); analysis of the new observation is left entirely to whichever `"analyzer"`-role worker(s) are configured, picked up asynchronously via their existing ticks (an `analyzer.source == "interval"` sweep over every enabled observable, or a scheduler-fired `type='analyze'` task claimed through `plugins/scheduler/`'s `claim_next_batch` — see "Shared pipeline" below) — the same rule-matching path (`services/reanalyze.lua` embedded, `worker_rule_matcher.lua` standalone) an analyze tick always uses, just not triggered synchronously from this route. This makes alerting for anything ingested this way (i.e. every standalone-worker-sourced observation, since that worker always POSTs here) eventually consistent rather than immediate, gated on an operator actually having an `"analyzer"`-role worker configured — not on this request itself.
- **`plugins/workers/`** — the worker registry that workers self-register/heartbeat into (`PUT /api/workers/:id/heartbeat`), plus bucketed heartbeat history (`GET /api/workers/:id/heartbeats`) for a connectivity histogram. Every worker also self-reports `roles` — a fixed, hardcoded set of roles (`analyzer`/`observer`/`deliver`/`scheduler`/`evaluator`, `worker_role_schemas.lua`; not user-editable like `observable_types`), and can declare more than one at once (the embedded worker reports `observer`+`analyzer` always, plus `scheduler` when `USE_EMBED_SCHEDULER=1`, `deliver` when `USE_EMBED_DELIVER=1`, and `evaluator` when `USE_EMBED_EVALUATOR=1`). `roles` gates which `properties` a worker may report — validated via `lib/property_schema.lua` against the concatenation of every declared role's fixed property schema (closed per role, so e.g. an observer-only worker can't report an analyzer-only field). `GET /api/workers?role=<role>` filters by declared role.
- **`plugins/scheduler/`** — admin-configured task definitions (`scheduler_tasks` table: a `type` — `observe`/`analyze`/`notify`, immutable after creation — plus either an observable-scoped target (`observable_type_id` + an explicit `observable_ids` list or a wildcard for every enabled observable of that type, for `observe`/`analyze`) or a notification-policy scope (`notify_policy_ids`, NULL/empty = every enabled policy, for `notify`), and a schedule — a `cron_expression` or a one-shot `run_at`) a `"scheduler"`-role worker evaluates periodically. `services/scheduler.lua`'s `fire_due` finds every due row and queues (or reuses) a single `status='pending'`, unassigned `jobs` row **per firing** (`type`=the task's own type, `ref_id`=the `scheduler_tasks.id`, `from_scheduler=true` — not one row per observable) — `jobs.worker_id` is nullable precisely for this; a partial unique index on `jobs (type, ref_id) WHERE status = 'pending'` means re-firing a recurring cron task before its previous pending job is claimed reuses that same row instead of stacking a duplicate — then advances `next_run_at` (cron, via the hand-rolled `shared/watchtower_worker_core/cron.lua`) or disables the row (one-shot, fires exactly once). `fire_due` deliberately never resolves or depends on the task's target — that's resolved lazily, fresh, only by whichever worker claims the job. `:claim_next_batch(worker_id, type)` atomically claims the oldest pending `jobs` row of `type` queued this way — assigning it to the calling worker and advancing it to `'triggering'` — for a role's priority pickup (for `observe`, ahead of, and entirely decoupled from, the existing continuous stalest-observable polling, `get_pending_observable`/`_fetch_observable_batch`, untouched); it then resolves the task's current target and returns it in full: `_resolve_observables` (the observable set) for `observe`/`analyze`, or, for `notify`, the task's policy scope (`notify_policy_ids`, absent = every enabled policy) and **nothing more** — an API route must never itself evaluate/decide, so the claim only hands out the scope and the worker does the matching. The `evaluator` role then runs `shared/watchtower_worker_core/notification_policy_matcher.lua` worker-side (see "Shared pipeline" below): it drains every candidate alert (one with no `alert_deliveries` rows yet, or with at least one row in `status='error'`, keyset-paged by id — keyset, not offset, since enqueuing removes alerts from that set while it is being paged, and because it drains the whole set an alert that matches no policy can't hold back newer ones), matches each against the scoped `notification_policies` (see `plugins/notification_channels/`'s bullet below), and **upserts** one `status='pending'` row per matched `(alert, channel)` pair onto the durable `alert_deliveries` queue (a row already `sent`/`pending`/`triggering` is left untouched; an `error` row resets to `pending` for retry), decoupled from whether/when anything actually gets sent. Claiming and evaluating a `notify` job is the **`evaluator`** worker role's entire job (see `plugins/notification_channels/`'s bullet below for the fully independent **`deliver`** role that actually drains and sends the queue this produces). The claiming worker runs entirely outside the ordinary per-observable `process_observable` flow (`shared/watchtower_worker_core/pollers/observe.lua`/`analyze.lua`/`evaluate.lua` — see "Shared pipeline" below): for `observe`/`analyze` it processes every observable in the claimed batch _without_ reporting a per-observable job for any of them, then reports exactly ONE final `acknowledged`/`error` on the batch job itself, with a summary `message` and a structured `result` — always passing `skip_rollup=true` (`plugins/jobs/services/jobs.lua`'s `report`/`report_error`) since the job's `ref_id` is a `scheduler_tasks.id`, not an `observables.id`; for `notify`, the report follows the worker's own matching pass. There is no separate run/audit table — `jobs` itself is the only record of a firing's outcome, one row per firing (`GET /api/jobs?ref_id=<task.id>&type=<type>`), not just summarized by `last_run_at`. Two worker-facing routes: `PUT /api/scheduler/fire-due` requires `WORKERS_WRITE` plus `JOBS_CREATE` (it's the one place a scheduler-fired `jobs` row is ever created); `PUT /api/scheduler/claim` requires `WORKERS_WRITE` plus `JOBS_READ` (finding/selecting a pending job - held by every consumer role except `scheduler` itself, which never calls `claim`). Admin CRUD + a `POST .../preview-cron` (no persistence) round out the plugin.
- **`plugins/jobs/`** — one row per work-assignment _attempt_ on a `(worker_id, type, ref_id)` target; `type` values are the verb form of the `workers.roles` role that produces them (see `plugins/workers/`'s bullet above). `type='observe'`/`type='observer_test'` (observer config test requests) are produced by ordinary per-observable paths (`from_scheduler=false`, `ref_id`=an `observables.id`/`observer_config_test_requests.id`); `type='observe'`/`type='analyze'`/`type='notify'` are also (and, for `analyze`/`notify`, _exclusively_) produced one row per firing by a scheduler task (`from_scheduler=true`, `ref_id`=a `scheduler_tasks.id`) — `from_scheduler` is what disambiguates `type='observe'`'s otherwise-polymorphic `ref_id` (the only type ever produced both ways); `analyze`/`notify` are always `from_scheduler=true`, never mistaken for an observable. `worker_id` is nullable: a `status='pending'` row with no `worker_id` is scheduler-queued work not yet claimed by anyone (see `plugins/scheduler/`'s `fire_due`/`claim_next_batch` above) — every other status always has a real `worker_id`. `services/jobs.lua`'s `report`/`report_error` upsert `ON CONFLICT (worker_id, type, ref_id) WHERE status = 'triggering'` — a _partial_ index (`jobs_active_unique_idx`), not a blanket-forever unique constraint — so a row is only ever updated in place while still in flight (`'triggering'`); once it reaches a terminal status (`'acknowledged'`/`'error'`) it's permanent history, and the _next_ attempt at that same `(worker_id, type, ref_id)` — a client retry, or a recurring scheduler task re-firing — inserts a fresh, independent row rather than colliding with or overwriting the finished one (`retries` still increments only on a same-status re-report of the _current_ in-flight attempt, never on forward progress). `_rollup` picks the _most recent_ row across every worker that's touched a `(type, ref_id)` (`ORDER BY created_at DESC`, not a status-priority ranking — deliberately, so one historical success can't mask every failure since) and writes it onto the per-type rollup target (`{manager, apply}` in `jobs/plugin.lua`) — only `type='observe'` has one, writing `observables.last_observe_status`/`last_observe_worker`/`last_observe_take_at`/`last_observe_ack_at`; `analyze`/`notify` are always reported with `skip_rollup=true` so `_rollup` never runs for them. `type='notify'` has no side effect in this module at all: the `evaluator` role enqueues onto `alert_deliveries` from its own worker-side matching pass (`shared/watchtower_worker_core/notification_policy_matcher.lua`), not as a side effect of this report, so by the time this module sees the report there's nothing left to apply — it's recorded exactly like any other type with no rollup entry. Actually sending a notification is a fully separate role/pipeline (`plugins/notification_channels/services/delivery_queue.lua`, see that plugin's bullet below) that never goes through this module's `report`/`report_error` at all — it claims/reports against `alert_deliveries` directly via its own `PUT /api/alert_deliveries/claim`/`.../report` routes. `GET /api/jobs?observable_type_id=` resolves the polymorphic `ref_id` through `scheduler_tasks` (`from_scheduler=true` rows) or `observables` (`from_scheduler=false` rows) depending on each row's own flag.
- **`plugins/notification_channels/`** — CRUD over `notification_channels` (discord/webhook destinations, a polymorphic bridge model like `models/notification_channels.lua`'s own `nc:create`/`update`/`include_options_in`) plus **notification policies** (`notification_policies` table), which route a fired alert to one or more channels — the same relationship `rules` has to observations, mirrored deliberately: a policy is authored via the identical flat `name`/`if`/.../`enabled` `source` document a rule is (reusing `shared/rule_engine/source.lua` directly, since it's a generic parser, not rules-specific), with `channels` (a comma-separated list of `notification_channels` ids) as the routing target, and its `if` evaluated via the same `shared/rule_engine/expr.lua` grammar against an ALERT's own fields (`severity`/`tags`/`rule_id`/`observable_id`, see `allowed_fields.lua`) rather than an observation's payload. `services/notification_policy_engine.lua` is only `test_expression` (`POST /api/notification_policies/test`, a side-effect-free dry run): real matching is worker-side (`shared/watchtower_worker_core/notification_policy_matcher.lua`, see "Shared pipeline" below), so the server keeps no policy-engine instance. `services/policies.lua` and `plugins/rules/services/rules.lua` are both thin specs over `lib/source_document_manager.lua`, which owns the shared derive/CRUD/export/import/search. The actual "send it" — `shared/watchtower_worker_core/notification_senders.lua` — is the first outbound-notification code in the repo: a `channel.type → sender` table (`webhook`: templated POST via `socket.http`/`ssl.https`; `discord`: `{content=...}` to a Discord incoming webhook), pure and DB-free so it runs identically on both worker runtimes (see "Shared pipeline" below). New permission quad `POLICIES_READ/CREATE/UPDATE/DELETE`, mirroring `CHANNELS_*`'s granularity.

  This plugin also owns the sender half of the notify pipeline: `services/delivery_queue.lua` is the **`deliver`** worker role's entire job, fully decoupled from `scheduler_tasks`/`jobs` (unlike every other worker-facing claim/report pair in this codebase) — `:claim_batch(worker_id, limit)` atomically claims up to `limit` `status='pending'` rows straight off the `alert_deliveries` queue (`UPDATE ... WHERE status='pending' ... FOR UPDATE SKIP LOCKED`, so more than one `deliver` worker can drain it concurrently without double-claiming a row — something the old scheduler-claim design never needed since only one worker ever claimed the single scheduler-fired job), resolves each claimed `(alert_id, channel_id)` pair's full alert/channel rows, and groups them by channel into the same `{channel, alerts, alert_ids}` shape `shared/watchtower_worker_core/notification_senders.lua`/`pollers/notify.lua` already expect; `:report(channel_results, worker_id)` then writes each row's own `status`/`notified_at`/`error_message` back, guarded on `status='triggering' AND worker_id=<claiming worker>` so a report can only resolve a row that worker actually claimed. Two worker-facing routes, `PUT /api/alert_deliveries/claim`/`.../report`, require `DELIVERIES_UPDATE` (a state transition on existing rows, like `jobs`' own report routes); the enqueue route (`POST /api/alert_deliveries`) requires both `DELIVERIES_CREATE` and `DELIVERIES_UPDATE`, since `delivery_queue:enqueue` genuinely both creates new matches and updates previously-errored ones for retry. Enqueuing (the `evaluator` role's worker-side `notification_policy_matcher.lua`, via `delivery_queue:enqueue`) and sending (here) share no state beyond the `alert_deliveries` rows themselves — see `alert_deliveries`'s own header comment in `config/dataset/init.sql` for the full `pending → triggering → sent | error` lifecycle, including how an `error` row gets retried.
- **`lib/`** — `plugins-service.lua` (the loader above), `routes.lua` (`compose`, `with_error_handling`, `capture_bad_request_params_validate`, `get_db_query_params_from_request_params`/`get_db_where_clause_from_request_params` — sort keys and search values are safely escaped, not interpolated raw — `pick_params`, `resolve_relative_date`, `with_transaction`), `resource_manager.lua` (generic CRUD/search manager most plugins build on), `models.lua` (`enhance_bridge_model`/`decorate_methods` for polymorphic bridge/subtype models, e.g. `notification_channels`).

### Shared pipeline (`shared/`) — used by both the standalone Lua worker and the embedded server worker

`shared/watchtower_worker_core/runner.lua`'s `build_config(mode)` is the single place `WORKER_CONFIG_FILE` (a `.lua` file, resolved through `config_provider.lua`/`config_provider_file.lua`, same directory) is loaded from. The server API key has its own precedence chain (`SERVER_API_KEY_FILE` → `SERVER_API_KEY` → `server.api_key` in the config file — most-secure-first; the file variant is how Docker/Compose secrets integrate with no extra code). `shared/watchtower_worker_core/processors.lua`'s `build_tasks(ctx, http_provider, utils)` is the **single** place the standalone worker's role → action mapping and each action's cadence live: an ordered array of `{name, role?, interval, retry_interval?, once?, run}` tasks (heartbeat first, then the ad-hoc test poller, the `"scheduler"` role's fire-due/reap-stale, the `"observer"` role's observe, then analyze, evaluate, notify — each included only when its role is in `config.roles`, each on its own `<role>.interval`). `shared/watchtower_worker_core/loop.lua` (`M.run(tasks, {clock, sleep, logger})`, generic and worker-agnostic — no luastash/pipeflow, which were dropped) drives it forever from `runner(opts)`: always runs the earliest-due task next, jittered ±20%, sleeps until the next one is due, `pcall`s every run, and lets `run()` return `ok, more` (`more` = due again immediately, used by `observer.source="interval"`'s one-observable-per-run drain, while every other due task still interleaves). Tasks run **sequentially**, so one slow task delays the others, but each role's `interval` is honoured independently (e.g. `deliver.interval=1` under a root `interval=10` really polls every ~1s) — the old luastash `input_http` loop instead slept the root `interval` per tick, so a role's interval could never be shorter than the root's. `run_once` (`--once`) iterates that same task table once (repeating a task while it returns `more`), so the loop and the one-shot pass can't drift apart. The observer's per-observable flow for `observer.source="interval"` is `process_observable` (report `processing` → `observe_observable` → report `error`, or `complete` = post the observation + report `acknowledged`), shared by `do_run_interval_observe` (standalone) and the embedded worker's `poll_pending_observe_interval`. `observe_observable` (`shared/watchtower_worker_core/processors.lua`) resolves the observable's observable type via `ctx.observable_types` (`shared/watchtower_worker_core/observable_type_cache.lua`, a tiny memoizing cache — HTTP-backed standalone, direct-model-backed embedded) and dispatches through `ctx.observer_registry` (`shared/watchtower_worker_core/observer_registry.lua`) — a routing mechanism: a plain `type string → handler` Lua table built from `WORKER_CONFIG_FILE`'s `observer.observers` array (`{id, type, observable_type, ...}`), keyed directly by observable-type name (no rule matching needed, since one observable has exactly one observable type). The one implemented observer type, `web_scraper` (`worker_plugins/watchtower_observer_web_scraper/observers/web_scraper.lua`), wraps `scraper_creator.lua`'s `WebScraper`, reading the URL from the observable's `properties` and coercing each extracted (always-string) field into the observable type's `observation_schema`-declared type. `scraper_creator.lua`'s `M.new(sites, transport)` optionally overrides the WebScraper instance's `_fetch` with an injected transport, mirroring `shared/watchtower_worker_core/notification_senders.lua`'s own transport DI: the embedded worker wires in `worker_plugins/watchtower_observer_web_scraper/resty_transport.lua` (cosocket-based `resty.http`, non-blocking) for both its observer registry and its ad-hoc test poller, since the vendored rock's own default `_fetch` is a blocking LuaSocket/LuaSec call that would stall that nginx worker's whole event loop — the same class of bug `resty_webhook_transport.lua` already fixed for outbound notifications — while the standalone worker keeps the vendored rock's own default fetch, since blocking is harmless in its plain Lua 5.1 process (numbers via `tonumber`, booleans matched against a truthy/falsy string set — `server/lib/property_schema.lua` hard-rejects a string for a `boolean`-typed property, so this coercion must happen worker-side before the properties are ever POSTed). An observer's site list normally comes from its own config (`sites`), but `sites_source = "remote"` instead fetches the current list via `deps.fetch_remote_sites()` (standalone: `GET /api/observer_configs/site`; embedded: `models.ObserverConfigs:select()`) — letting sites be managed centrally on the server instead of duplicated into every worker's own config. That fetch happens at construction time, and is re-run inline, as part of that one observer's own `:run` (`worker_plugins/watchtower_observer_web_scraper/observers/web_scraper.lua`'s `M:_refresh_remote_sites`, checked immediately before each observe) - not a separate task/timer, and not anything `observer_registry.lua`/`runner.lua` know about, deliberately: loading sites is specific to a `sites_source="remote"` observer, so the refresh lives entirely inside that observer type's own module rather than as generic state on the registry. Each observer's own `remote_sites_refresh_interval` (in `WORKER_CONFIG_FILE`'s `observer.observers` array; a plain hardcoded literal for the embedded worker's one observer) sets that one observer's own cadence, independently of any other `sites_source="remote"` entry this worker declares - a refresh failure logs and keeps the previous, still-working site list rather than replacing it with an empty one. `shared/analyzer.lua` is the other reusable role: given an ingested observation, matches it against every enabled rule and creates the resulting alert(s) — dependency-injected (`M.new(rule_engine, alert_manager, log_error)`, no `require("plugins...")` of its own) so it's usable by anything that _can_ construct those two objects. The matching orchestration itself (the match context and its memoized `changed`-baseline fetcher, alert derivation, already-alerted/cooldown suppression) is `shared/watchtower_worker_core/rule_matching.lua`, shared by `analyzer.lua` (SQL-backed) and `worker_rule_matcher.lua` (HTTP-backed) so the two can't drift; `POST /api/rules/test*` builds its context through the same `rule_matching.build_context`. One call site remains, deliberately outside `POST /api/observations` (see `plugins/entities/` above — that route only ever inserts the observation row now): the embedded worker's own module-level `analyzer`, called directly from `ingest_observation` (its own in-process observe path, unrelated to the HTTP route) since it has no plugin-composed `deps` at nginx-worker-boot time, and again from its `"analyzer"`-role ticks (both routing through `reanalyze.lua`). The standalone worker does not use `shared/analyzer.lua` at all — it has no direct Postgres access by design; its `"observer"`-role tick POSTs every observation to `POST /api/observations`, which — since that route stopped analyzing inline — now only ever persists it, and its own `"analyzer"`-role tick instead runs `shared/watchtower_worker_core/worker_rule_matcher.lua`, a from-scratch DB-less mirror of this same matching logic driven entirely over HTTP. Self-reported `roles` for the heartbeat come from `config.roles` (`build_config`'s output — standalone: `WORKER_CONFIG_FILE`'s optional `roles` array, default `{"observer"}`; embedded: always `{"observer","analyzer"}` plus `"scheduler"` when `USE_EMBED_SCHEDULER=1`, `"deliver"` when `USE_EMBED_DELIVER=1`, and `"evaluator"` when `USE_EMBED_EVALUATOR=1`), not a hardcoded literal — this is what lets a worker declare `"scheduler"` alone. The `"scheduler"` role's tick is its own task (standalone: a task in `build_tasks` on `scheduler.interval`; embedded: its own `ngx.timer.every`, mirroring the ad-hoc test-poller's precedent) — it only ever calls `plugins/scheduler/`'s `fire_due`, via `shared/watchtower_worker_core/pollers/scheduler.lua`'s `poll_and_run` (a thin wrapper, included alongside the other four roles' own `pollers/*.lua` for symmetry even though this role has no claim/report split of its own). The `"analyzer"`/`"evaluator"` roles' ticks are two more such independent loops — `shared/watchtower_worker_core/pollers/analyze.lua`/`evaluate.lua`, exactly mirroring `pollers/observe.lua`'s claim→process→one-final-report shape (see below) for their own `"queue"` mode (the default, and today's only mode for `notify`'s claim path): `analyze_observable` re-runs rule matching against an observable's latest stored observation (embedded: `plugins/entities/services/reanalyze.lua` in-process; standalone: `worker_rule_matcher.lua`'s own client-side matching); `notify`'s claim only hands out the task's policy scope, and `pollers/evaluate.lua` then runs the worker's own `evaluate` dep (`notification_policy_matcher.lua`: alert/policy matching AND enqueueing onto `alert_deliveries`, scoped to that task's policies) and reports its outcome. Both roles also support a second, independent `"interval"` mode (`config.analyzer.source`/`config.evaluator.source`, mirroring `observer.source` below) — a periodic full sweep with **no** `scheduler_tasks`/`jobs` row involved at all, bypassing `pollers/analyze.lua`/`evaluate.lua` entirely: `analyzer`'s tick is the same `processors.lua` `do_run_interval_analyze_all` on both runtimes, routing through the `reanalyze.lua`/`worker_rule_matcher.lua` matching each already uses for `"queue"` mode; `evaluator`'s tick (`do_run_interval_evaluate_notify`) runs the very same worker-side `notification_policy_matcher.lua` pass its `"queue"` mode runs per claimed task, just over every enabled policy — in-process for the embedded worker (policies from the model, candidate alerts from `server/lib/alert_queries.lua`, enqueue via `delivery_queue:enqueue`), over HTTP for the standalone one, fed only by narrow, non-evaluating server endpoints (`GET /api/notification_policies?enabled=true`, `GET /api/alerts?needs_delivery=true` keyset-paged with `after_id`+`sort=id:asc`, `POST /api/alert_deliveries`) rather than a server-side "evaluate" call, since an API route must never itself evaluate/decide (see this file's own "worker jobs never run in an API endpoint" rule, further above). The `"deliver"` role's tick is a **fourth**, differently-shaped independent loop: unlike the other three, by default (`deliver.source = "deliveries"`) it has no `scheduler_tasks`/`jobs` involvement whatsoever — `shared/watchtower_worker_core/pollers/notify.lua` claims a batch directly off the `alert_deliveries` queue (`plugins/notification_channels/services/delivery_queue.lua`'s `:claim_batch`/`:report`, see that plugin's bullet above) and dispatches via `shared/watchtower_worker_core/notification_senders.lua`, identical on both runtimes since all policy matching already happened earlier, independently, inside the `"evaluator"` role's own matching pass; `deliver.source = "queue"` instead claims a scheduler-fired `type='deliver'` job whose claim forwards to that same queue claim (and reports the wrapping job too). The embedded worker injects its own non-blocking sender (`ctx.notification_sender`, built on the cosocket transports) into that shared tick. An `"observer"`-role worker's own `config.observer.source` (`"queue"`, the default, or `"interval"`) is an explicit either/or, not a hybrid: `"interval"` is the original continuous stalest-observable polling (`get_pending_observable`/`_fetch_observable_batch`), run one observable per call through `process_observable` (standalone: the `observe_interval` task via `do_run_interval_observe`, which chains via `more` until `http_provider:next()` reports the sweep exhausted; embedded: `poll_pending_observe_interval`, one stalest observable per `observer.interval` tick). `"queue"` mode's observing, however, does **not** go through `process_observable` at all — it runs via `shared/watchtower_worker_core/pollers/observe.lua`, a third independent poller of the same shape (claim → observe every observable in the claimed batch → one final report), run as the standalone loop's `observe_batch` task (`shared/watchtower_worker_core/processors.lua`'s `do_run_pending_observe_batch`) or the embedded worker's own `ngx.timer.every` running that same `do_run_pending_observe_batch` (`server/workers/observe_pending_worker.lua`) — gated on `has_role(config.roles, "observer") and config.observer.source == "queue"`. It reuses `shared/watchtower_worker_core/processors.lua`'s `observe_observable` (the same dispatch-through-`ctx.observer_registry` logic `process_observable` wraps for the interval path) for each observable, but posts each observation and reports the batch's single final status without ever going through `process_observable`'s per-observable `processing`/`complete` job reports — so a fresh deployment with `observer.source="queue"` (the default) and no `scheduler_tasks` task yet observes nothing, same as before, but once one exists a firing observes its whole observable set as one job, not one job per observable.

The embedded worker (`server/workers/observe_pending_worker.lua`, `USE_EMBED_WORKER=1`) runs every role's tick as the very same shared function the standalone worker runs (`processors.lua`'s exported `do_*`), each on its own `ngx.timer.every`, with `embedded_provider` — the in-process counterpart of `provider_http.lua`, exposing the same method names but calling the services directly (no HTTP) — as its transport; it also registers itself before its first job report (`jobs.worker_id` has an FK to `workers`). It builds one `observer_registry` entry per distinct `observable_type_id` with at least one enabled `plugins/observer_configs` row, each always `sites_source = "remote"` against that table directly (a real DB query, no HTTP) — it does not read `WORKER_CONFIG_FILE`'s `observer.observers` key at all. An observable type with no enabled `observer_configs` row simply gets no observer registered, a safe no-op rather than an error. That observer registry is built **inside** the `ngx.timer.at(0, ...)` registration callback, not at module top level — same "attempt to yield across C-call boundary" trap `bootstrap_admin.lua` avoids; a bare `pcall` around a top-level DB call silently swallows that error and leaves the worker with zero registered sites forever, which is exactly what happened during this port's own verification before the fix, so the query itself is still wrapped in a `pcall` that degrades to zero observers on failure rather than aborting boot. The `"scheduler"` role's tick (gated on `USE_EMBED_SCHEDULER=1`, independent of `USE_EMBED_WORKER`) is its own concurrent `ngx.timer.every`, same pattern as the ad-hoc test-poller's `start_test_poll` — every embedded role runs on its own `ngx.timer.every` (no shared loop, so a slow role never delays another); `shared/watchtower_worker_core/loop.lua` is standalone-only. `observer.source == "interval"` is served by `poll_pending_observe_interval` (started from `start_worker_with_heartbeat`'s timer callback right after worker registration since it reports per-observable `jobs` rows): it calls the untouched `get_pending_observable()` (the single stalest enabled observable, once per `observer.interval` tick) and hands it to `processors.process_observable` with `notifier` (the in-process `processing`/`complete`/`error` job-manager wrapper). `"queue"` mode (default) is served by the shared `do_run_pending_observe_batch` on its own concurrent `ngx.timer.every` (gated on the `"observer"` role and `observer.source == "queue"`, like every embedded role's tick), which claims a scheduler-fired batch job, observes every observable in it via `shared/watchtower_worker_core/processors.lua`'s `observe_observable`, ingests each observation directly (`post_observation`, no per-observable job report), and reports the batch's one final status via `job_manager` with `skip_rollup=true`.

The standalone worker (`worker/lua/main.lua` + `shared/watchtower_worker_core/provider_http.lua`) does everything over HTTP with an API key, for whichever roles its `config.roles` declares: claims scheduler-fired batches (`PUT /api/scheduler/claim`), observes and `POST`s `/api/observations`, matches rules and policies client-side (`worker_rule_matcher.lua`, `notification_policy_matcher.lua`), claims and sends deliveries, and reports job outcomes via `PUT /api/jobs/:type/:id/{triggering,ack,error}`. `provider_http.lua`'s `_call`/`_job_report`/`_fetch_page` are the one request-and-unwrap path every method goes through.

The jobs related to workers never should be done in the API endpoint from the server.

### Frontend (`public/`) — Vue 3, Pinia + Tailwind

Every plugin (`entities`, `notification_channels`, `observer_configs`, `security`, `rules`, `alerting`, `workers`, `scheduler`, `jobs`) is Pinia + Tailwind, driven by `public/src/core/services/plugin-service.js`: `stores/createListStore.js` is the shared server-side search/filter/sort/paginate factory every list store is built on; `components/common/DataTable.vue` + `TableFilterBar.vue` is the shell every list view composes; `core/router.js`'s single `beforeEach` guard reads `to.meta.permission`/`.public` (set by `core/services/app-service.js`'s `registerApp`) against the `auth` Pinia store. `main.js` awaits `useAuthStore().restore()` before mounting so the guard never sees an unhydrated store. `core/Layout.vue` is a Tailwind sidebar (explicit collapse/expand toggle persisted to `localStorage`, off-canvas overlay on small screens) that filters its nav list the same way; nav icons are hand-drawn inline-SVG components under `components/common/icons/`, not an icon font.

**New views should be built from `components/common/` pieces wherever the feature fits an existing component's shape** — any new list/table view should use `DataTable` + `TableFilterBar`, matching how `RulesListView`/`AlertsListView`/`UsersListView`/`RolesListView`/`ApiKeysView`/`JobsListView`/`ObservablesListView`/`ObserverConfigsListView`/`NotificationChannelsListView`/`ObservationsListView` already do.

**Every displayed server timestamp goes through `utils/date.js`'s `formatDate`** (browser timezone/locale; it also handles the API's bare-UTC `TIMESTAMP` strings) — never render a date column/field raw (`DataTable` falls back to the raw value when a column has no `#cell-<key>` slot, so every date column needs one) and never call `toLocaleString` ad hoc.

Domain components shared across more than one plugin (`AlertStatusBadge`, `AlertSeverityBadge`, `AlertDetailsFlyout`, `WorkerConfigFlyout`) live at the top level of `components/`, not nested inside one plugin's own `views/` — both `alerting` and `jobs`/`workers` reference them.

### Users & roles, rule engine

Same live-enforcement design — see `plugins/security/`'s section above. No user or role is hardcoded; `users`/`roles` are real Postgres tables seeded only with the three default roles (`admin`/`operator`/`viewer`), never any user rows.

### `docker/` layout

All four images below create a dedicated, unprivileged `watchtower` user (uid/gid
`1000`, via `addgroup`/`adduser`) at build time and switch to it with `USER` before
their final `CMD`/`ENTRYPOINT` — none of them run as root at container start. Port
8080 needs no privileged-port capability, and `server/nginx.conf` has no `user`
directive, so nginx's master and worker processes both simply run as this same
non-root user rather than the master staying root and dropping worker processes to
`nobody` (nginx's normal behavior when its master itself starts as root). Their
third-party LuaRocks dependencies are version-pinned via `docker/rockspecs/*.rockspec`
(`watchtower-server-deps-1.0-1.rockspec` for the two Lapis images,
`watchtower-worker-deps-1.0-1.rockspec` for the two standalone-worker images) —
plain dependency-listing rockspecs with `build = {type = "none"}`, installed via
`luarocks-5.1 install --only-deps <file>`, which resolves only their `dependencies`
table (each pinned `== <version>`) without ever fetching/building the rockspec's own
(nonexistent) source — instead of the old bare, unversioned `luarocks-5.1 install
<name>` lines.

- `docker/images/dev/lapis/` — dev OpenResty+Lapis image (`entrypoint.sh` runs every plugin's `setup.sh`, e.g. the scraper plugin's `webscraper`/`xml` install fix). Its build context is the repo root (like the dev worker image below), so it can also pre-bake that same `setup.sh`/`xml.rockspec` fix at build time — `entrypoint.sh`'s runtime re-run of `setup.sh` is then a no-op (its own `luarocks-5.1 show` checks skip already-installed rocks), since the container's runtime user has no `apk`/`luarocks` write access to install anything fresh.
- `docker/images/dev/worker/` — standalone worker image: Lua 5.1 + LuaRocks built from source on Alpine (no OpenResty needed), reusing the scraper plugin's `setup.sh`/`xml.rockspec` fix for `webscraper`, plus `lua-cjson`/`luasec`/`luasocket`.
- `docker/images/prod/server/` — two-stage build: Node 22 frontend build, then the same OpenResty+Lapis image as dev (`production` mode). `/app`/`/shared` are `chown`'d to the service user after everything is `COPY`'d in (build stages still run as root, as normal), so nginx can create its pid/log files and temp dirs there at runtime.
- `docker/images/prod/worker/` — same Lua 5.1/LuaRocks build as the dev worker image, but with `worker/lua/`+`shared/` baked in (`COPY`, not bind-mounted) and a `LUA_PATH` that includes `/worker_plugins` by default, so a bind-mounted `worker_plugins/` volume (the `WORKER_CONFIG_FILE` `plugins` field's external-module mechanism) works out of the box under any orchestrator, not just this repo's own compose files. Published to `ghcr.io/<repo>-worker` alongside the server image by `.github/workflows/docker-publish.yml` on every version tag.
- `docker/worker/worker_config.example.lua` — the full `WORKER_CONFIG_FILE` reference.
